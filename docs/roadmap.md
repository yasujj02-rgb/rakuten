## Phase 5 設計: 定期価格監視・通知

### 前提条件（実装前に確認）
1. 楽天ウェブサービス利用規約でのデータ保存・キャッシュ期間の許容範囲（価格推移の保存可否）
2. 通知手段（メール / Web Push / LINE 等）の無料枠と規約

### 構成案
```
Cron Trigger（例: 1 日 2 回）
  → D1 の watch テーブル（お気に入りをサーバーへ同期した分）を取得
  → SpacingQueue で 1 件ずつ検索（既存の searchRakuten / rankProducts をそのまま再利用）
  → 目標単価を下回る・ポイントアップ開始・値下げを検知
  → notifications テーブルで (watchId, itemCode, 条件, 値) の重複を排除
  → 通知送信（頻度設定: 即時 / 1 日 1 回まとめ）
```

- お気に入り・設定はサーバー保存が必要になるため、D1 に `watches`（検索条件・目標単価・ポイント設定のスナップショット）と
  `notifications`（送信済みキー・送信日時）を作成。価格そのものは規約確認まで保存しない。
- 無料枠の見積り: 監視 20 件 × 1 日 2 回 = 40 API コール / 日、Worker 実行 2 回 / 日。D1 の読み書きも数百行 / 日で無料枠内。
- Cron の 1 回の実行時間（CPU 時間）は待機時間を含まないため、1.1 秒間隔の直列取得でも CPU 制限には掛かりにくい。
  件数が増えた場合は Queues または Durable Objects で分割する。

### 実装順
1. `src/worker/scheduled.ts`（`scheduled` ハンドラ）と D1 マイグレーション
2. お気に入りのサーバー同期 API（認証済みユーザーのみ）
3. 判定ロジック（shared に純粋関数として追加しテスト）
4. 通知アダプタ（インターフェースを定義し、手段ごとに実装）
